# Internationalization (i18n)

How Bramble localizes every user-facing string across all targets, and how translations are
generated. English is the source of truth and lives inline in the code; translations are produced by
a local (or optional API) LLM into per-target catalogs, then validated in CI and at release.

## Bottom line

- **English stays inline.** You write `<Trans>Unlock vault</Trans>` (web) or `getString(...)` /
  `String(localized:)` (native). There is no separate "key file" to keep in sync; the English text is
  the message id.
- **Four targets, one engine.** The web/extension UI, iOS native autofill, Android native autofill,
  and the iOS App Store metadata each have their own catalog format. A single set of Node scripts
  (`scripts/i18n/`) translates all of them from one shared locale list via a local Ollama model
  (default) or DeepSeek (optional).
- **CI and release refuse to ship gaps.** `pnpm i18n:check` fails if any catalog has a missing entry.
- **Supported locales:** `en` (source) + `de`, `es`, `fr`, `pt-BR`, `it`.

## Locales

The single source of truth is `scripts/i18n/locales.mjs`. Each locale maps its catalog code to the
per-platform conventions:

| Web / Lingui | App Store (fastlane) | Android (`res/values-…`) | Language |
| ------------ | -------------------- | ------------------------ | -------- |
| `de`         | `de-DE`              | `de`                     | German   |
| `es`         | `es-ES`              | `es`                     | Spanish  |
| `fr`         | `fr-FR`              | `fr`                     | French   |
| `pt-BR`      | `pt-BR`              | `pt-rBR`                 | Brazilian Portuguese |
| `it`         | `it`                 | `it`                     | Italian  |

To add a locale: add one row to `LOCALES` in `scripts/i18n/locales.mjs`, add its code to
`locales` in `packages/core/src/i18n.ts` and the `locales` array in `lingui.config.ts`, then run
`pnpm i18n` and `pnpm i18n:native`.

## Targets

### 1. Web / extension / mobile webview (`@core`) — Lingui

The shared React UI in `packages/core/src/app/` uses [Lingui](https://lingui.dev) macros.

- **JSX text:** `<Trans>Create new vault</Trans>` (supports interpolation: `<Trans>Welcome to
  {appName}</Trans>`).
- **Strings (attributes, validation, variables):** the `` t`` `` tag from `useLingui()`, e.g.
  ``placeholder={t`Master password`}`` or ``t`Remove ${name}` ``.
- **Strings in non-component code** (e.g. the entry-mode descriptors in `app/entry-modes/*.tsx`):
  the lazy `msg` macro from `@lingui/core/macro` rendered with `i18n._(msg`...`)`. `label`/`description`
  on the descriptor objects are getters so they re-evaluate against the active locale; methods like
  `row()` / `detailAlert()` wrap their returned strings inline.

Runtime: `packages/core/src/i18n.ts` lazily imports the active locale's compiled catalog
(`activateLocale`), so each bundle ships only the language in use (per-locale `messages-*.js`
chunks). `App` (`app/App.tsx`) detects the locale before first paint:

- Extension / dev browser: `navigator.language`.
- Mobile: the `preferredLocale` prop, which `platform-mobile/src/main.tsx` reads from
  `@capacitor/device` `getLanguageTag()`. This is necessary because iOS WKWebView clamps
  `navigator.language` to the app bundle's declared localizations and would otherwise default to
  English on a non-English device.

`resolveLocale` matches a BCP-47 tag against the supported set (exact first, then bare language, so
`pt-BR` and `pt` both resolve, `es-419` → `es`).

Catalogs live in `packages/core/src/locales/<locale>/`:

- `messages.po` — the catalog (committed source of truth, holds the translations).
- `messages.ts` — compiled output the runtime imports (regenerate with `i18n:compile`).

#### Build wiring (important)

The macros are transformed by **Babel via `vite-plugin-babel`**, not `@vitejs/plugin-react`. The
project's `@vitejs/plugin-react` is the oxc-based v6 with **no `babel` option**, so a macro config
passed to it is silently ignored — the bundle would keep `@lingui/*/macro` imports and crash at
runtime. The shared helper `scripts/vite-lingui.mjs` (`linguiMacroPlugin()`) runs the Lingui macro in
a bundler-agnostic transform hook and is used by both platform `vite.config.ts` files and
`packages/core/vitest.config.ts`. To sanity-check a build actually transformed the macros, grep
`dist/` for `@lingui/react/macro` — it must be absent.

### 2. iOS native autofill — String Catalog

The credential-provider extension (`platform-mobile/ios/App/AutoFillProbe/
CredentialProviderViewController.swift`) is pure SwiftUI and does not touch the webview. Its strings
go through `String(localized:)` and a String Catalog at `AutoFillProbe/Localizable.xcstrings`
(wired into the `AutoFillProbe` target's resources + `knownRegions` in `project.pbxproj`). iOS picks
the locale from the device automatically. Format specifiers are `%@` (string) and `%lld` (int).

Note: the biometric icon is derived from `LAContext.biometryType`, not by string-matching the
(now-localized) label, so the Face ID / Touch ID icon stays correct in every language.

### 3. Android native autofill — string resources

The autofill service (`platform-mobile/android/.../app/bramble/mobile/*.kt`) reads strings via
`getString(R.string.…)` from `res/values/strings.xml`, translated into `res/values-<qualifier>/
strings.xml`. Android selects the locale at runtime. Format args are `%s` / `%d`; apostrophes are
escaped to `\'`. Identifiers (`package_name`, `custom_url_scheme`) and the brand `app_name` are
marked / treated non-translatable.

### 4. iOS App Store metadata — fastlane

`platform-mobile/ios/App/fastlane/metadata/<appStore>/*.txt`. Prose files (`description`,
`promotional_text`, `release_notes`, `subtitle`) are translated; `name` and the URL files are copied
verbatim. After translating, a **second AI "fit" pass** shortens any field that overruns its App
Store cap (`keywords` ≤ 100, `subtitle` ≤ 30, `promotional_text` ≤ 170), with a deterministic
fallback so a field is never left over-length.

## Commands

```sh
# Web catalogs (the common loop):
pnpm i18n               # extract -> translate -> compile
pnpm i18n:extract       # scan source for macros, update .po catalogs
pnpm i18n:translate     # fill empty .po entries via the LLM
pnpm i18n:compile       # compile .po -> messages.ts for the runtime

# Every surface (web + iOS xcstrings + Android xml + fastlane), all idempotent:
pnpm i18n:native

# Validate completeness (no model; used by CI and release):
pnpm i18n:check         # fail if any catalog has missing entries
node scripts/i18n-check.mjs --extract   # also re-extract first (catches new, untranslated strings)
```

All commands are idempotent: translation only fills entries that are still empty, so re-running after
adding strings translates just the new ones.

## Translation backend

By default everything runs **fully offline through local [Ollama](https://ollama.com)** — no API key,
nothing leaves the machine (it fits the project's privacy stance).

- Default model: `gemma4:e4b-mlx` (Apple Silicon). Pull it with `ollama pull gemma4:e4b-mlx`.
- Override via env: `I18N_MODEL`, `OLLAMA_HOST`, `I18N_CHUNK`.

Optionally use **DeepSeek** (faster, higher quality, but sends UI strings to a third party):

1. `cp .env.example .env.local` and set `DEEPSEEK_API_KEY=sk-...` (`.env.local` is gitignored).
2. Run `pnpm i18n:translate` / `pnpm i18n:native` — they load `.env.local` and route to DeepSeek
   automatically when the key is present.

The translator (`scripts/i18n/ollama.mjs`) pins a **formal register**, preserves placeholders, keeps
brand/standard terms (Bramble, Face ID, TOTP, KeePass, AES-256-GCM) untranslated, and **guards
placeholder integrity** — if a translation drops or mangles a placeholder (e.g. `%@` → `@`) it
retries, then falls back to translating that string alone. `<think>…</think>` scratchpads from
reasoning models are stripped.

> qwen3 was tried and rejected: this Ollama build ignores `think:false`/`/no_think`, so it emitted
> ~2k reasoning tokens per string. Gemma has no thinking mode and is the right local default.

## CI and release gates

- **CI** (`.github/workflows/ci.yml`): runs `node scripts/i18n-check.mjs --extract`. The `--extract`
  re-runs Lingui extraction first, so a new source string that was never translated surfaces as a
  missing entry and fails the build. No model runs in CI.
- **Release** (`scripts/release.ts` `gate()`): runs `pnpm i18n:check` (committed-state, no
  `--extract`) so a tag can never ship with missing translations.

The AI generation step is intentionally **not** run in GitHub-hosted CI (the default model is MLX /
Apple-Silicon; CPU GGUF is slow). Translation is a local/on-demand step that commits filled catalogs;
CI only verifies completeness. To automate it, use a self-hosted runner, a nightly job, or the
DeepSeek backend, and have it open a PR.

## Typical workflows

**Added or changed web UI strings:**

```sh
# wrap them in <Trans> / t`` / msg`` first, then:
pnpm i18n          # extract + translate + compile
pnpm i18n:check    # confirm green
```

**Added native (Swift/Kotlin) or store strings:**

```sh
# add to Localizable.xcstrings / res/values/strings.xml / fastlane en-US, then:
pnpm i18n:native   # translates the new entries into every locale + fits store caps
pnpm i18n:check
```

**Verifying a build actually localized:**

- Web: `pnpm --filter @vault/platform-extension build` then grep `dist/` for `@lingui/*/macro`
  (must be empty).
- iOS: `xcrun xcstringstool compile AutoFillProbe/Localizable.xcstrings --output-directory /tmp/x`
  validates the catalog; a real `xcodebuild` bundles the `.lproj` into the appex.
- Android: `./gradlew :app:processDebugResources` validates every `values-*/strings.xml` via aapt.

## Caveats

- Output reflects the model. A small local model produces occasional artifacts (e.g. a dropped
  hyphen in a keyword); **human review before release is worthwhile**, especially for non-European
  languages where small models are weaker.
- There is no in-app locale **picker** yet; locale follows the OS/browser. Add one later if needed.
- After adding a Capacitor plugin (like `@capacitor/device`, used for locale detection), run
  `npx cap sync` so the native projects register it.
